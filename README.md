# Roomside


## Run

Install Node.js 20+ and npm, then double-click `run.command` on macOS, or run `./run.sh` in a terminal. The first run installs dependencies and opens the app in your browser. You can also run `npm install` and `npm start`. The development server listens on this computer only (`127.0.0.1`); the optional phone mirror opens one more port on your network, only while it is on. Use a browser with Web Speech API support (Chrome is recommended). Browser speech recognition availability and audio processing depend on the browser and its provider.

## Desktop app

The Tauri 2 shell is scaffolded as an installable desktop app, including a Roomside app icon. On macOS, install Xcode Command Line Tools, Node.js 20+, and Rust, then double-click `desktop.command` (or run `npm install` followed by `npm run desktop`). `npm run desktop:build` creates a release bundle. Windows needs the Microsoft C++ Build Tools and WebView2; Linux needs the Tauri WebKitGTK build dependencies. The shell requests microphone permission with a clear macOS usage description. If the system webview does not expose its speech recognition API, use the browser launcher or type questions manually.

Without Rust installed locally, you can build the desktop app on GitHub: open **Actions → Desktop build → Run workflow** and tick the macOS option to download `Roomside.app` (unsigned, so right-click it and choose **Open** the first time). The same workflow compiles the shell on Linux whenever `src-tauri/` changes.

If macOS blocks the microphone, open the site in Chrome and allow microphone access for `127.0.0.1` in the address bar/site settings. If speech recognition is unavailable or network speech processing is disabled, type the question in the manual field. For model errors, confirm the endpoint and model name, then verify that the endpoint accepts browser CORS requests.

## Tests

Run `npm test` for the Vitest unit tests (they need Node.js 22.12 or newer); GitHub Actions runs them, plus the production build, on every push and pull request. They cover question detection, answer formatting, conversation memory, the OpenAI-compatible and demo answer providers (with `fetch` mocked), Deepgram message handling, how browser speech recognition starts, restarts, and fails, and the phone mirror's relay, secret link, and tab handover (over real local HTTP servers).

## Answers from your Claude subscription

With `npm start`, Roomside can answer through [Claude Code](https://code.claude.com) signed in with your Claude account, so there is no API key and usage counts toward your plan. Sign Claude Code in once (it opens your browser):

```sh
claude auth login
```

If `claude` is not on your PATH, use the copy bundled with the Claude desktop app: `"$HOME/Library/Application Support/Claude/claude-code/<version>/<build>/claude.app/Contents/MacOS/claude" auth login` (older versions of the app have no `<build>` folder). Roomside finds that copy itself, the newest version first. Roomside then picks **Claude, with your Claude subscription** automatically and answers with Claude Haiku 5.5, which thinks briefly before it answers; choose Claude Haiku 4.5 in Settings for the fastest start, or Claude Sonnet 5.5. The dev server runs Claude Code with every tool disabled, in an empty temporary folder, and only for requests from the Roomside page itself (`server/claude-code-bridge.ts`); the question goes over stdin, not the command line. It also leaves out your own Claude Code setup (CLAUDE.md, hooks, plugins, and skills) and extended thinking, so the first words usually appear in about a second, and it keeps one Claude Code process started ahead of the next question so answers do not wait for it to boot; that idle process uses none of your Claude usage. Set `CLAUDE_BIN` to use a specific Claude Code binary. This bridge exists only in the dev server, not in `npm run build` or the desktop app.

## Phone mirror

With `npm start`, you can follow the session on your phone: open **Phone** in the top bar, choose **Start phone mirror**, and scan the QR code with your phone's camera. The phone shows the listening state, what was just heard, the detected question, the main question, the live coach's notes, and the suggested answer as it streams. From the phone you can start or stop listening, type a question, tap **Answer now** beside it to answer what was just said (in case a question was missed), tap a line under **Transcript** (the last 30) to answer it or its label to switch it between Interviewer and You, switch between Short, Standard, Detailed, and Bullets, ask for a shorter, expanded, follow-up, or regenerated answer or for **Follow-up on my answer**, tap **↻** beside the coach for fresh tips, fix a misheard question with the pencil on the live answer (**Answer this instead** answers it in place, as on the laptop), open the list of main questions from **2 of 3 ▾** beside the current one (a tap on one shows where it was asked, when the phone's transcript still has that line), and pin or unpin any answer with the pin on its card. The pinned answer waits above the list (its **Show** goes to its card, or opens it there when the phone no longer has the card), and the pin at the bottom left jumps to it. Answers run oldest to newest; the phone follows the newest while you are on it, and otherwise keeps your place and offers **New answer ↓**. **↑ Previous** and **Next ↓** at the bottom step from question to question (Question 3 of 7). Audio still comes only from the laptop's microphone, so keep Roomside open there (it can stay in the background).

- The phone must be on the same network as the laptop. Campus and office Wi-Fi often block connections between devices; if the page does not load, connect the laptop to your phone's hotspot and scan again.
- The phone page runs on a second server (`server/phone-mirror.ts`) that starts only while mirroring is on and answers only under a random secret link, which changes every time you start. Anyone with the link on your network can see the session and control listening until you stop mirroring. Phones receive only text (transcript, question, answer); your context files are never sent, and the Claude Code bridge still accepts requests only from this computer. The link is plain HTTP on your local network.
- Only one Roomside tab is mirrored at a time. Reloading that tab keeps the phone connected; if you open another tab, the Phone mirror panel lets you move the mirror to it.
- Phone browsers do not let plain-HTTP pages keep the screen awake, so turn off Auto-Lock (or keep tapping) while you practice.

## Providers

- **Speech recognition:** choose the browser's built-in `SpeechRecognition` / `webkitSpeechRecognition` adapter, or select Deepgram streaming and enter an API key in Settings. For technical interviews, Deepgram is the more accurate option: Roomside uses its Nova-3 model with keyterm prompting for common interview terms (LeetCode, Two Sum, Big O, …) plus any **Extra words to recognize** you add, and its diarization to split an utterance into turns when two people speak. Either way, answers are written to recover misheard technical terms from context. Both run through a replaceable `SpeechToTextProvider` interface. A local voice detector (an AudioWorklet, so it keeps working while the tab is in the background) tracks the room's noise level to show when someone is speaking, starts answering as soon as a question-sounding sentence ends, and measures pitch and tone for telling speakers apart; it does not record or transmit audio. Roomside turns echo cancellation off for its microphone input, since it plays nothing while listening and Chrome's canceller can remove an interviewer whose call plays from another tab on the same computer. Browser transcription may use its speech service; Deepgram mode streams microphone audio directly to Deepgram. The API key stays in memory and is sent in the WebSocket handshake, not its URL. To skip pasting it every session, copy `.env.example` to `.env` and set `DEEPGRAM_API_KEY`: with `npm start`, Roomside fills in the key and switches transcription to Deepgram, and Settings shows that the key came from `.env`. The dev server gives it only to the Roomside page on this computer (`server/deepgram-key.ts`), and `npm run build` never includes it.
- With the browser's built-in recognition in Chrome 140 or newer, **Boost interview vocabulary** in Settings runs recognition on-device and boosts the same interview terms plus your extra words (Chrome downloads its speech model once; Settings offers the download). If the model is missing or Chrome rejects the word list, Roomside notes it above the transcript and keeps using standard recognition. On-device recognition can be less accurate for everyday speech, so leave it off if it does worse for you.
- Use **Test transcription connection** to verify Deepgram access without turning on the microphone or sending audio.
- Select a transcription language in Settings (English, Spanish, French, German, Brazilian Portuguese, Japanese, or Mandarin Chinese). Connected AI providers are prompted to answer in the question's language; offline demo responses use English sample content.
- In Deepgram mode, **Detect microphones** lists inputs after you explicitly grant mic permission; choose the room mic or keep System default. Browser built-in recognition uses the operating system's default microphone and restarts itself after brief network drops.
- **Answer generation:** works offline with streaming demo answers. To use a model, open Settings and configure an OpenAI-compatible chat completions endpoint, model, and optional API key. Answers stream as server-sent events; endpoints that reply with a single JSON response also work, and models that only accept their default temperature are retried without one. Requests go only to the endpoint you enter. Keys and transcripts remain in page memory and are cleared on refresh/close. The endpoint must allow browser cross-origin requests (CORS).

## Controls

- Start / Stop Listening: start or stop recognition; Escape stops listening (or closes Settings). Words still being recognized when you stop are kept in the transcript.
- Type a question and press Enter (or `⌘/Ctrl + Enter` from anywhere) to submit it. With nothing typed, `⌘/Ctrl + Enter` is **Answer now**.
- Answers remember the whole conversation: every question is sent with the transcript so far (up to about 40,000 characters, which covers a typical 45 to 60 minute interview; beyond that the opening and the most recent part are kept), so a later question can refer back to anything said earlier. Typed questions join the transcript too.
- **Main questions** (Settings, on by default) keeps track of the overarching question or case you are working through, after the introductions: "our client is a coffee chain whose profits fell 20%; how would you find out why?", a coding problem, or "tell me about yourself", which the smaller questions, hints, and back-and-forth then happen around. A quick check by your answer provider reads the transcript soon after a new question comes up, and otherwise every half minute or so while you talk, rewording the main question as it gets clearer. The current one is pinned above the answers (and on the phone mirror), with the list so far a click away there too; clicking one shows where it was asked in the transcript, and the refresh button beside it checks again right away. Answers and the coach use it, so "what would you look at first?" is answered as part of the case. Saved sessions keep their main questions.
- **Live coach** (Settings, on by default with Live answer) is pinned above the answers, so it stays in view however the answer scrolls, and shows on the phone mirror too. It is a separate request to your answer provider (Claude, for most people), made the moment each question is asked, that reads the question, the conversation, and what you say: **Key** is the one idea your answer has to land, then two or three short points you have not made yet, and a **tip** on how you are coming across when there is something to fix (running long, no example yet, a lot of filler words, not answering the question). It points to specifics from **Your context** (the actual project, class, or result from your résumé and notes, tied to the role and company you are interviewing for), never "mention something specific"; when the role or your background is missing, it says so and links to Context, and coaches the question again once you add them. It follows the conversation about the question, your answer and the interviewer's hints, updating at most every 8 seconds once a dozen more words have been said, and stops at the goodbyes. The refresh button beside it (**↻** on the phone mirror) asks for fresh tips for the question right away, from the conversation as it is at that moment (including words still being spoken), and different from the ones on screen. Reading a suggested answer aloud does not move it.
- **Review** (top bar) shows how you answered each question in the session, measured from the transcript: how many words and roughly how long, how much you read from a suggested answer, filler words ("um", "like", "you know", repeated words), and checks for the kind of question (for coding: a clarifying question, an example, an edge case, and the complexity; for behavioral: a specific situation, what you did, and the result). A summary gives the questions answered, your share of the talking, how much you read aloud, and filler words a minute. **Coach me** asks your answer provider for one strength and one thing to practice per question, plus the three habits to work on most (with Claude, a little of your usage). It works on a saved session you open again too, so you can practice and then look back.
- **Tell speakers apart** (Settings, on by default) labels each transcript line Interviewer or You. Roomside first guesses from the wording (questions and prompts are the interviewer's, first-person accounts are yours), then a quick background check by Claude Haiku, or by your OpenAI-compatible model, reads a few lines at a time in context and fixes wrong guesses; with Deepgram, voices are told apart too. With the browser's recognition, Roomside also compares how each line sounded (pitch, brightness, and loudness, measured on this computer from the microphone) with how each person has sounded so far, so a line that says little ("yeah, that makes sense") is still labeled by voice. Each stretch of speech is also compared with the line still open: someone who sounds clearly different (a different pitch, backed up by loudness or brightness) ends the line with their first words, while the same voice going on after a pause keeps it open. With Deepgram, sound also checks its voice numbers: a number that flips mid-turn in the same voice is merged, one that stays the same across two clearly different voices is split (and not credited to the new speaker), and a number with no label yet is labeled by how it sounds. Every line keeps what its own speech sounded like, never the next person's, and a laugh or cough ends nothing. **Learn my voice** in Settings records 8 seconds of you reading a sentence, so your lines are recognized from the start; only a few numbers about your voice are kept, in memory for this tab. Your own clarifying questions ("can I assume…", "should I…") are not answered. A line that repeats one of the last few suggested answers (or the pinned one) is you reading it aloud, even loosely and with misheard words: it is labeled You whatever the voice or wording suggests, never gets an answer of its own, and teaches Roomside your voice. A question you read from one is never taken for the interviewer's either, even when the recognizer runs it together with what they just said. When the interviewer cuts in while you are talking or reading ("…and before that I was at, oh, so how was that?"), their words get their own line and an answer, and if you reply in the same breath, your reply gets a line too; the answer to their question starts while they are still asking it. Click a label to correct it (or tap it on the phone mirror), and use **All / Interviewer / You** above the transcript to show one side. Answers see who said what, and the phone mirror shows the labels. The check skips the Claude Code process kept ready for answers, so answers stay fast.
- Hover a transcript line and click **↵** to answer it (on the phone mirror, tap the line): for a question Roomside did not catch, or one run together with other words.
- **Answer now** (beside the model's name above the answers, at the bottom of the phone mirror, or `⌘/Ctrl + Enter` with nothing typed) answers what was just said, for when a question was missed or taken for your own words: back to the latest line that is the interviewer's or sounds like a question, whoever it was labeled as (but not past the question the live answer is on), with the words still being said.
- **Sessions:** click the session title at the top left. **Save this session** keeps its transcript (the memory answers use, with speaker labels), answers, and pinned answer in this browser on this computer, and from then on it saves itself as it changes. The same menu names the session, starts a **New session**, and lists saved sessions to reopen or delete. A reopened session picks up where it left off: new speech adds to it, and answers remember everything said before. Nothing is saved unless you choose to; Clear conversation and New session leave a saved session as it was and start a fresh, unsaved one.
- Clear conversation removes the transcript, its memory, and the current answer without stopping the microphone.
- Connected AI providers are prompted to sound like you explaining something to another engineer: natural contractions, concrete actions and reasons, and a mix of sentence lengths. They avoid résumé language, canned openings, forced hesitation, and a polished moral at the end of every answer. Coding problems use SAY (a brief approach), CODE (a runnable solution in the requested language, else your strongest from your résumé, else Python), and CHECK (time, space, and one edge case). System design gets scope questions, the main flow and storage choice, a useful sketch, and a concrete trade-off. Behavioral answers use your background as an anchor and fill small gaps with plausible details. Personal questions draw on **Your context** when available and can fill in a missing personal detail naturally. Employers, titles, credentials, awards, named projects, and metrics stay grounded in context. Follow-ups answer the new point without restarting the full format. Earlier conversation and suggested answers help avoid repeated openings and stories.
- Choose Short, Standard, Detailed, or Bullets for all answers. The quick actions are one-off requests for a shorter, expanded, or likely follow-up answer and keep the selected mode; the top line of each answer card shows which mode produced it. **Follow-up on my answer** (once you have said something to the question) is the follow-up the interviewer would likely ask about what you actually said, from the transcript: something specific you said, such as a choice, a claim, a number, or what you left out. It shows that question, then a brief suggested answer.
- **Live answer** (Settings, on by default): one answer at the top of Answers keeps up with the conversation. Each question or problem the interviewer puts to you gets a fresh answer, found even when the recognizer runs their question into your reply or labels it wrong ("…What is the overall complexity? O of m plus n." answers the complexity question). It grows while they set up what they are asking or trail off mid-question, and starts before their line is final once the question sounds finished (with Deepgram, when it ends in a question mark; with browser recognition, when they pause on a question that does not trail off), so it is written once rather than rewritten while they talk, and never from half a question. Then it holds still: asides, hints, small talk, and listening noises ("mm-hmm", "okay, so") leave it alone. So do your own questions about the problem ("so are we talking about internal systems, or customers?", "do we need to handle concurrency?") and your own words said like a question, whoever the line is labeled as; an interviewer asking what "we" would do without saying "you" ("how would we scale this?") is taken the same way, so use ↵ on that line. While you read it aloud nothing changes, and neither does the question it answers said again, whether you read it back or they repeat it. When the interviewer asks something new, the answer so far moves to **Earlier**, a collapsed list below it, newest first. While you are reading an earlier answer, it stays exactly where it is on screen: the live answer streaming, the finished one moving under Earlier, or the coach resizing above it never pull you away, and **Live answer ↑** jumps back. Each card shows what it responds to (with the time and question type) above the answer. Regenerating, asking for a shorter or longer version or a follow-up, and switching modes keep the previous version under Earlier, so nothing you read is lost. Live answers and key points use more of your Claude usage than answering questions only; turn the setting off to answer only what sounds like a question. The phone mirror shows the same answers, and Clear conversation empties them.
- Misheard question? Click the pencil on the latest card (here or on the phone mirror) and fix it right there: **Enter** answers the corrected question in place on the same card (and corrects its transcript line, so later answers remember the right words), and **Esc** cancels.
- Pin any answer (the pin on its card, here or on the phone mirror, or `⌘/Ctrl + P` for the latest) to keep it one click away above the list; **Show** scrolls back to it.
- Read aloud is available when the microphone is off, so the app does not transcribe its own voice.
- **Your context** (**Context** in the top bar): add the role you are interviewing for, notes about yourself (including what you do for fun, which personality questions draw on), and files such as your résumé or the job description (PDF, Word .docx, text, or Markdown). Files are read in the browser and never uploaded as files; their text, up to 40,000 characters, is sent with each question to your answer provider so Claude can answer as you and tell stories from your real projects. If the background leaves gaps, the prompt allows plausible details to complete a story while keeping employers, titles, credentials, awards, named projects, and metrics tied to your context. It stays in memory unless you turn on **Keep on this computer**, which saves only the extracted text in this browser; turning it off deletes that copy. With `npm start`, your résumé is added automatically every time Roomside opens: any PDF, Word, text, or Markdown file in the project folder with "resume" in its name, or the files listed in `CONTEXT_FILES` in `.env` (see `.env.example`). Only the dev server reads them, only the Roomside page on this computer receives them, and `.gitignore` keeps résumé files out of git.
- Use **Test connection** in Settings to check a remote provider before starting. It sends a small test prompt to the configured endpoint.
- `⌘ + Shift + Space` on macOS (`⌘ + Space` opens Spotlight) or `Ctrl + Space` elsewhere toggles listening, `Escape` stops, `⌘/Ctrl + 1` requests a short answer, `⌘/Ctrl + 2` requests a detailed answer, and `⌘/Ctrl + P` pins/unpins the current answer. Shortcuts are paused while Settings is open, and Settings lists them all.
- Enable **Clear transcript when stopping** in Settings to discard transcript and answer context when ending microphone listening.

## Current scope

The desktop shell is scaffolded but has not been compiled or packaged in this environment. Recognition uses browser interim/final events and provider-specific behavior; question detection is heuristic (it recognizes spoken lead-ins such as “so, what…” and question cues for each supported language, since browser recognition adds no punctuation), starts a draft from the words still coming (for a live answer, the interviewer's words; otherwise a likely question, debounced or as soon as the voice stops after one), keeps that draft when the final wording matches, and otherwise revises from the final speech segment. Words that may be yours never start a draft, so reading an answer aloud cannot change it before the line is final. A pause does not split what someone says across transcript lines: a line stays open while its speaker keeps talking and until they have been quiet long enough for what they said. A finished-sounding question commits as soon as the voice detector hears silence, so its answer is not held up; a sentence cut off mid-phrase ("How would you design…" … "a URL shortener") waits nearly two seconds for the rest; anything else waits out about a second with Deepgram (just over half a second with browser recognition, unless the two learned voices sound clearly apart, since otherwise it cannot tell them apart). Once both voices are learned and distinct, the same person going on after a pause gets nearly two seconds. A voice that sounds like someone else ends the line at once, and with Deepgram so does another voice number, unless it flipped mid-sentence. The voice detector keeps this working in background tabs, where Chrome slows timers down. Low browser confidence is surfaced as “Possible question.” Manual Question is available when recognition is unavailable. The web app type-checks and builds with Node.js 24; desktop builds also require Rust, which has not been installed here.
