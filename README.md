# Roomside


## Run

Install Node.js 20+ and npm, then double-click `run.command` on macOS, or run `./run.sh` in a terminal. The first run installs dependencies and opens the app in your browser. You can also run `npm install` and `npm start`. The development server listens on this computer only (`127.0.0.1`); the optional phone mirror opens one more port on your network, only while it is on. Use a browser with Web Speech API support (Chrome is recommended). Browser speech recognition availability and audio processing depend on the browser and its provider.

## Desktop app

The Tauri 2 shell is scaffolded as an installable desktop app, including a Roomside app icon. On macOS, install Xcode Command Line Tools, Node.js 20+, and Rust, then double-click `desktop.command` (or run `npm install` followed by `npm run desktop`). `npm run desktop:build` creates a release bundle. Windows needs the Microsoft C++ Build Tools and WebView2; Linux needs the Tauri WebKitGTK build dependencies. The shell requests microphone permission with a clear macOS usage description. If the system webview does not expose its speech recognition API, use the browser launcher or type questions manually.

Without Rust installed locally, you can build the desktop app on GitHub: open **Actions → Desktop build → Run workflow** and tick the macOS option to download `Roomside.app` (unsigned, so right-click it and choose **Open** the first time). The same workflow compiles the shell on Linux whenever `src-tauri/` changes.

If macOS blocks the microphone, open the site in Chrome and allow microphone access for `127.0.0.1` in the address bar/site settings. If speech recognition is unavailable or network speech processing is disabled, type the question in the manual field. For model errors, confirm the endpoint and model name, then verify that the endpoint accepts browser CORS requests.

## Tests

Run `npm test` for the Vitest unit tests (they need Node.js 22.12 or newer); GitHub Actions runs them, plus the production build, on every push and pull request. They cover question detection, answer formatting, conversation memory, the OpenAI-compatible and demo answer providers (with `fetch` mocked), Deepgram message handling, how browser speech recognition starts, restarts, and fails, and the phone mirror's relay, secret link, and tab handover (over real local HTTP servers).

## Answers from your Claude subscription

With `npm start`, Roomside can answer through [Claude Code](https://code.claude.com) signed in with your Claude account, so there is no API key and usage counts toward your plan. Sign Claude Code in once (it opens your browser):

```sh
claude auth login
```

If `claude` is not on your PATH, use the copy bundled with the Claude desktop app: `"$HOME/Library/Application Support/Claude/claude-code/<version>/claude.app/Contents/MacOS/claude" auth login`. Roomside then picks **Claude, with your Claude subscription** automatically; choose Claude Haiku 4.5 (fastest) or Claude Sonnet 5 in Settings. The dev server runs Claude Code with every tool disabled, in an empty temporary folder, and only for requests from the Roomside page itself (`server/claude-code-bridge.ts`); the question goes over stdin, not the command line. It also leaves out your own Claude Code setup (CLAUDE.md, hooks, plugins, and skills) and extended thinking, so the first words usually appear in about a second, and it keeps one Claude Code process started ahead of the next question so answers do not wait for it to boot; that idle process uses none of your Claude usage. Set `CLAUDE_BIN` to use a specific Claude Code binary. This bridge exists only in the dev server, not in `npm run build` or the desktop app.

## Phone mirror

With `npm start`, you can follow the session on your phone: open **Phone** in the top bar, choose **Start phone mirror**, and scan the QR code with your phone's camera. The phone shows the listening state, what was just heard, the detected question, and the suggested answer as it streams. From the phone you can start or stop listening, type a question, switch between Short, Standard, Detailed, and Bullets, and ask for a shorter, expanded, follow-up, or regenerated answer. Audio still comes only from the laptop's microphone, so keep Roomside open there (it can stay in the background).

- The phone must be on the same network as the laptop. Campus and office Wi-Fi often block connections between devices; if the page does not load, connect the laptop to your phone's hotspot and scan again.
- The phone page runs on a second server (`server/phone-mirror.ts`) that starts only while mirroring is on and answers only under a random secret link, which changes every time you start. Anyone with the link on your network can see the session and control listening until you stop mirroring. Phones receive only text (transcript, question, answer); your context files are never sent, and the Claude Code bridge still accepts requests only from this computer. The link is plain HTTP on your local network.
- Only one Roomside tab is mirrored at a time. Reloading that tab keeps the phone connected; if you open another tab, the Phone mirror panel lets you move the mirror to it.
- Phone browsers do not let plain-HTTP pages keep the screen awake, so turn off Auto-Lock (or keep tapping) while you practice.

## Providers

- **Speech recognition:** choose the browser's built-in `SpeechRecognition` / `webkitSpeechRecognition` adapter, or select Deepgram streaming and enter an API key in Settings. For technical interviews, Deepgram is the more accurate option: Roomside uses its Nova-3 model with keyterm prompting for common interview terms (LeetCode, Two Sum, Big O, …) plus any **Extra words to recognize** you add, and its diarization to split an utterance into turns when two people speak. Either way, answers are written to recover misheard technical terms from context. Both run through a replaceable `SpeechToTextProvider` interface. A local voice detector (an AudioWorklet, so it keeps working while the tab is in the background) tracks the room's noise level to show when someone is speaking, starts a draft answer as soon as a question-sounding sentence ends, and measures pitch and tone for telling speakers apart; it does not record or transmit audio. Roomside turns echo cancellation off for its microphone input, since it plays nothing while listening and Chrome's canceller can remove an interviewer whose call plays from another tab on the same computer. Browser transcription may use its speech service; Deepgram mode streams microphone audio directly to Deepgram. The API key stays in memory and is sent in the WebSocket handshake, not its URL. To skip pasting it every session, copy `.env.example` to `.env` and set `DEEPGRAM_API_KEY`: with `npm start`, Roomside fills in the key and switches transcription to Deepgram, and Settings shows that the key came from `.env`. The dev server gives it only to the Roomside page on this computer (`server/deepgram-key.ts`), and `npm run build` never includes it.
- With the browser's built-in recognition in Chrome 140 or newer, **Boost interview vocabulary** in Settings runs recognition on-device and boosts the same interview terms plus your extra words (Chrome downloads its speech model once; Settings offers the download). If the model is missing or Chrome rejects the word list, Roomside notes it above the transcript and keeps using standard recognition. On-device recognition can be less accurate for everyday speech, so leave it off if it does worse for you.
- Use **Test transcription connection** to verify Deepgram access without turning on the microphone or sending audio.
- Select a transcription language in Settings (English, Spanish, French, German, Brazilian Portuguese, Japanese, or Mandarin Chinese). Connected AI providers are prompted to answer in the question's language; offline demo responses use English sample content.
- In Deepgram mode, **Detect microphones** lists inputs after you explicitly grant mic permission; choose the room mic or keep System default. Browser built-in recognition uses the operating system's default microphone and restarts itself after brief network drops.
- **Answer generation:** works offline with streaming demo answers. To use a model, open Settings and configure an OpenAI-compatible chat completions endpoint, model, and optional API key. Answers stream as server-sent events; endpoints that reply with a single JSON response also work, and models that only accept their default temperature are retried without one. Requests go only to the endpoint you enter. Keys and transcripts remain in page memory and are cleared on refresh/close. The endpoint must allow browser cross-origin requests (CORS).

## Controls

- Start / Stop Listening: start or stop recognition; Escape stops listening (or closes Settings). Words still being recognized when you stop are kept in the transcript.
- Type a question and press Enter (or `⌘/Ctrl + Enter` from anywhere) to submit it.
- Answers remember the whole conversation: every question is sent with the transcript so far (up to about 40,000 characters, which covers a typical 45 to 60 minute interview; beyond that the opening and the most recent part are kept), so a later question can refer back to anything said earlier. Typed questions join the transcript too.
- **Tell speakers apart** (Settings, on by default) labels each transcript line Interviewer or You. Roomside first guesses from the wording (questions and prompts are the interviewer's, first-person accounts are yours), then a quick background check by Claude Haiku, or by your OpenAI-compatible model, reads a few lines at a time in context and fixes wrong guesses; with Deepgram, voices are told apart too. With the browser's recognition, Roomside also compares how each line sounded (pitch, brightness, and loudness, measured on this computer from the microphone) with how each person has sounded so far, so a line that says little ("yeah, that makes sense") is still labeled by voice. Each stretch of speech is also compared with the line still open: someone who sounds clearly different (a different pitch, backed up by loudness or brightness) ends the line with their first words, while the same voice going on after a pause keeps it open. With Deepgram, sound also checks its voice numbers: a number that flips mid-turn in the same voice is merged, one that stays the same across two clearly different voices is split (and not credited to the new speaker), and a number with no label yet is labeled by how it sounds. Every line keeps what its own speech sounded like, never the next person's, and a laugh or cough ends nothing. **Learn my voice** in Settings records 8 seconds of you reading a sentence, so your lines are recognized from the start; only a few numbers about your voice are kept, in memory for this tab. Your own clarifying questions ("can I assume…", "should I…") are not answered. A line that repeats one of the last few suggested answers (or the pinned one) is you reading it aloud, even loosely and with misheard words: it is labeled You whatever the voice or wording suggests, never gets an answer of its own, and teaches Roomside your voice. When the interviewer cuts in while you are talking or reading ("…and before that I was at, oh, so how was that?"), their words get their own line and an answer, and if you reply in the same breath, your reply gets a line too; a draft answer to their question starts as soon as they finish. Click a label to correct it, and use **All / Interviewer / You** above the transcript to show one side. Answers see who said what, and the phone mirror shows the labels. The check skips the Claude Code process kept ready for answers, so answers stay fast.
- Hover a transcript line and click **↵** to answer it: for a question Roomside did not catch, or one run together with other words.
- **Sessions:** click the session title at the top left. **Save this session** keeps its transcript (the memory answers use, with speaker labels), answers, and pinned answer in this browser on this computer, and from then on it saves itself as it changes. The same menu names the session, starts a **New session**, and lists saved sessions to reopen or delete. A reopened session picks up where it left off: new speech adds to it, and answers remember everything said before. Nothing is saved unless you choose to; Clear conversation and New session leave a saved session as it was and start a fresh, unsaved one.
- Clear conversation removes the transcript, its memory, and the current answer without stopping the microphone.
- Answers sound like a sharp 19–20-year-old student interviewing for an internship or co-op: first person, plain words, straightforward, no corporate buzzwords. Coding problems come back as the whole thinking process: THE PROBLEM (restated, with a tiny example and any clarifying question), MY THINKING (brute force, then the better idea), WHAT I'D USE (data structures and why), PSEUDOCODE, CODE (full solution, in the language asked for, else your strongest from your résumé, else Python), COMPLEXITY, and EDGE CASES. Behavioral answers tell a short, real story from your background; concept questions are explained in a few plain sentences with an example. Questions about you as a person (what you do for fun, how your friends would describe you, your best quality, what motivates you) are answered from your personality and life outside work, using the hobbies and interests in **Your context**, rather than turning every answer into an internship story, and nothing new about you is made up. Each answer also sees the last few suggested ones, so it opens differently and picks a different story or example.
- Choose Short, Standard, Detailed, or Bullets for all answers. The quick actions are one-off requests for a shorter, expanded, or likely follow-up answer and keep the selected mode; the top line of each answer card shows which mode produced it.
- Answers form a running list: each card shows the question it answers (with the time and question type) above the answer, newest at the bottom. Scroll up for earlier answers; while you are reading one, new answers do not pull you away, and **New answer ↓** jumps to the latest. Regenerating, asking for a shorter or longer version or a follow-up, and switching modes add a card instead of replacing one, so nothing you read is lost (a draft started from unfinished speech is updated in place). The phone mirror shows the same list, and Clear conversation empties it.
- Misheard question? Click the pencil on the latest card and fix it right there: **Enter** answers the corrected question in place on the same card (and corrects its transcript line, so later answers remember the right words), and **Esc** cancels.
- Pin any answer (the pin on its card, or `⌘/Ctrl + P` for the latest) to keep it one click away above the list; **Show** scrolls back to it.
- Read aloud is available when the microphone is off, so the app does not transcribe its own voice.
- **Your context** (**Context** in the top bar): add the role you are interviewing for, notes about yourself (including what you do for fun, which personality questions draw on), and files such as your résumé or the job description (PDF, Word .docx, text, or Markdown). Files are read in the browser and never uploaded as files; their text, up to 40,000 characters, is sent with each question to your answer provider so Claude can answer as you and tell STAR stories from your real projects; it may fill in believable details of a moment, but never new jobs, titles, or metrics. It stays in memory unless you turn on **Keep on this computer**, which saves only the extracted text in this browser; turning it off deletes that copy. With `npm start`, your résumé is added automatically every time Roomside opens: any PDF, Word, text, or Markdown file in the project folder with "resume" in its name, or the files listed in `CONTEXT_FILES` in `.env` (see `.env.example`). Only the dev server reads them, only the Roomside page on this computer receives them, and `.gitignore` keeps résumé files out of git.
- Use **Test connection** in Settings to check a remote provider before starting. It sends a small test prompt to the configured endpoint.
- `⌘ + Shift + Space` on macOS (`⌘ + Space` opens Spotlight) or `Ctrl + Space` elsewhere toggles listening, `Escape` stops, `⌘/Ctrl + 1` requests a short answer, `⌘/Ctrl + 2` requests a detailed answer, and `⌘/Ctrl + P` pins/unpins the current answer. Shortcuts are paused while Settings is open, and Settings lists them all.
- Enable **Clear transcript when stopping** in Settings to discard transcript and answer context when ending microphone listening.

## Current scope

The desktop shell is scaffolded but has not been compiled or packaged in this environment. Recognition uses browser interim/final events and provider-specific behavior; question detection is heuristic (it recognizes spoken lead-ins such as “so, what…” and question cues for each supported language, since browser recognition adds no punctuation), starts a debounced draft from likely question partials (or as soon as the voice stops after one), keeps that draft when the final wording matches, and otherwise revises from the final speech segment. A pause does not split what someone says across transcript lines: a line stays open while its speaker keeps talking and until they have been quiet long enough for what they said. A finished-sounding question commits as soon as the voice detector hears silence, so its answer is not held up; a sentence cut off mid-phrase ("How would you design…" … "a URL shortener") waits nearly two seconds for the rest; anything else waits out about a second with Deepgram (just over half a second with browser recognition, unless the two learned voices sound clearly apart, since otherwise it cannot tell them apart). Once both voices are learned and distinct, the same person going on after a pause gets nearly two seconds. A voice that sounds like someone else ends the line at once, and with Deepgram so does another voice number, unless it flipped mid-sentence. The voice detector keeps this working in background tabs, where Chrome slows timers down. Low browser confidence is surfaced as “Possible question.” Manual Question is available when recognition is unavailable. The web app type-checks and builds with Node.js 24; desktop builds also require Rust, which has not been installed here.
